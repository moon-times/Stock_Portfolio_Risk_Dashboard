지금 대화에 이미 나온 내용만으로 **명세 파일 하나**를 만든다.

**사용자를 새로 인터뷰하지 않는다.** 이미 안 것을 합성하는 게 전부다. 대화에서 안 나온 내용을 지어내지 않는다.

## 절차

### 1. 지금 상태를 본다

프로젝트 폴더에 뭐가 있는지 확인한다. `CLAUDE.md`, `specs/tech-stack.md` 가 있으면 읽는다. 거기 적힌 제약을 명세가 어기면 안 된다.

### 2. 빈 칸을 확인한다

아래 템플릿에서 **대화에 안 나온 항목**을 목록으로 뽑아 사용자에게 보여준다.
각 빈 칸마다 **네가 추천하는 답을 함께 제시**한다. 사용자가 "그걸로 하자"만 말하면 되게 만든다.

빈 칸이 3개를 넘으면 명세를 쓰지 말고 **"`/grill-me` 를 먼저 돌리는 게 낫습니다"** 라고 말한다.

### 3. 파일을 쓴다

`specs/spec-<짧은-영문-슬러그>.md` 로 저장한다. `specs/` 폴더가 없으면 만든다.
**이미 같은 이름의 파일이 있으면 덮어쓰지 말고 사용자에게 묻는다.**

<명세-템플릿>

# <기능 이름>

## 문제

**누가 / 언제 / 무엇 때문에 막히는가.** 사용자 입장에서 쓴다.
해결책이나 기술 이름을 여기 쓰지 않는다.

## 해결

그 문제가 사라진 뒤의 모습. **사용자 입장에서** 쓴다.

## 사용자 스토리

번호를 붙인 목록. 각 줄은 이 형식이다.

1. **<누구>** 로서, 나는 **<무엇>** 을 하고 싶다. 그래야 **<무엇이 좋아진다>**.

예: 1. 자취생으로서, 나는 냉장고에 남은 재료를 입력하고 싶다. 그래야 장을 두 번 보지 않는다.

빠짐없이 쓴다. 화면에 보이는 것, 눌렀을 때 일어나는 것, 잘못 눌렀을 때 일어나는 것을 모두 포함한다.

## 정한 것

만들면서 이미 정해진 것들. 예: 데이터를 어디에 저장하는가, 화면이 몇 개인가, 무엇을 무엇으로 부르는가.
**파일 경로나 코드 조각은 쓰지 않는다.** 금방 낡는다.

## 만들지 않을 것

이번 명세의 범위 밖. **여기가 비어 있으면 명세가 아니다.** 최소 세 줄은 쓴다.

## 확인 방법

다 됐는지 사람이 눈으로 확인하는 방법. 각 줄을 아래 형식으로 쓴다.

- **Given** (어떤 상태에서) / **When** (무엇을 하면) / **Then** (무엇이 보인다)

예: **Given** 저장된 재료가 하나도 없는 상태에서 / **When** 입력창에 "달걀"을 치고 엔터를 누르면 / **Then** 목록에 "달걀"이 보인다

</명세-템플릿>

### 4. 끝내고 안내한다

파일 경로를 알려주고 한 줄 덧붙인다 —
**"이걸 만들 수 있는 크기로 쪼개려면 `/to-tickets` 를 치세요."**
