## UC-01. 대시보드 조회 (정상 경로)

> **주 성공 시나리오다.** 다른 모든 유스케이스는 이 흐름의 변형이다.

| 항목 | 내용 |
|---|---|
| **목표** | 실계좌 데이터로 포트폴리오 리스크를 확인한다 |
| **선행조건** | `.env`에 유효한 토스증권 키·계좌번호·Anthropic 키가 설정됨. 인터넷 연결됨 |
| **후행조건** | 6개 블록이 모두 렌더링되고 폴백 배지가 없다 |
| **트리거** | 터미널에서 `streamlit run app.py` 실행 |

### 주 흐름

| # | 액터 | 시스템 |
|---|---|---|
| 1 | `streamlit run app.py` 실행 | 브라우저 자동 오픈, 스피너 표시 |
| 2 | | `Settings` 로드 → `TOSS_CLIENT_ID`/`SECRET` 존재 확인 |
| 3 | | `token.json` 확인 → 유효하면 재사용, 아니면 `POST /oauth2/token` (FR-101, FR-101a) |
| 4 | | `GET /api/v1/accounts` → `accountSeq` 해석 (FR-102) |
| 5 | | `GET /api/v1/exchange-rate` → `midRate` 확보 |
| 6 | | `GET /api/v1/holdings` (`X-Tossinvest-Account`) → items 파싱 (FR-102a, FR-102b) |
| 7 | | `GET /api/v1/buying-power` KRW·USD 2회 → 현금 합산 (FR-103, FR-103a) |
| 8 | | 계좌번호 마스킹 적용 (FR-105) |
| 9 | | `GET /api/v1/stocks?symbols=...` 1회 → 자산군 분류 (FR-301, FR-301a) |
| 10 | | 자산군별 집계 → `AllocationBreakdown` (FR-304) |
| 11 | | `GET /api/v1/market-indicators/prices?symbols=KR_BOND_3Y` → `/100` (FR-206) |

| 14 | | 비중가중 포트폴리오 수익률 시계열 산출 |
| 15 | | 리스크 지표 6종 계산 (FR-401~406) |
| 16 | | 자산군 간 상관계수 행렬 계산 (FR-501) |

| 18 | | 지표 페이로드 → Claude API → `Commentary` (FR-701) |
| 19 | | 헤더 + 메트릭 4개 + 도넛 + 리스크표 + 히트맵 + 라인차트 + AI배너 렌더링 |
| 20 | 화면 확인 | |

### 수용 기준

- [ ] 20단계까지 15초 이내 (NFR-101, 약 28콜)
- [ ] 2회차 실행 시 3단계에서 토큰 재발급이 일어나지 않는다 (FR-101a)
- [ ] 12단계 캔들 루프에서 429가 발생하지 않는다 (FR-201b)
- [ ] 샤프지수 절댓값이 10 미만이다 (무위험수익률 단위 검증, FR-402a)
- [ ] 폴백 배지 미표시
- [ ] 리스크 지표에 `N/A` 없음
- [ ] AI 코멘트가 실제 계산값을 인용 (FR-702)
- [ ] 계좌번호 뒤 4자리만 노출 (FR-105)
- [ ] 자산배분 비중 합계 100% ± 0.1%p (FR-304)

## UC-02. 자격증명 없이 실행

| 항목 | 내용 |
|---|---|
| **목표** | API 키가 없어도 앱이 동작함을 확인한다 (발표 대비, 신규 사용자 온보딩) |
| **선행조건** | `.env` 없음, 또는 `USE_MOCK_DATA=true` |
| **후행조건** | 샘플 데이터로 전체 화면이 렌더링되고 배지가 표시된다 |
| **대응 요구사항** | FR-104, FR-803 |

### 흐름

| # | 시스템 |
|---|---|
| 1 | `settings.has_broker_credentials == False` 판정 |
| 2 | `MockBrokerClient(fallback_reason="자격증명 없음")` 생성 |
| 3 | `data/sample_portfolio.json` 로드 → `Portfolio(is_fallback=True)` |
| 4 | 가격 히스토리는 실제 `/candles` 호출 시도 (샘플 종목이 실존하므로 가능). 토큰조차 없으면 이 단계도 실패 → UC-10 |
| 5 | 이후 UC-01의 10~19단계와 동일 |
| 6 | 화면 상단에 `샘플 데이터로 표시 중입니다 (자격증명 없음)` 경고 표시 |

### 수용 기준

- [ ] 앱이 크래시하지 않는다
- [ ] 6개 블록 모두 렌더링된다
- [ ] 폴백 배지가 명확히 보인다
- [ ] `ANTHROPIC_API_KEY`도 없으면 규칙 기반 코멘트가 나온다

> **왜 P0인가**: 발표 당일 API 키가 만료되거나 증권사 점검이 걸려도 데모가 성립해야 한다. 또한 채점자가 자기 환경에서 실행해 볼 때 키 없이도 화면을 볼 수 있어야 한다.

| 항목 | 내용 |
|---|---|
| **목표** | LLM이 실패해도 진단 코멘트 영역이 비지 않는다 |
| **선행조건** | 포트폴리오·지표 계산은 성공 |
| **대응 요구사항** | FR-705, FR-706 |

### 흐름

| # | 시스템 |
|---|---|
| 1 | Claude API 호출 (타임아웃 10초) |
| 2 | 다음 중 하나 발생: 타임아웃 / 인증 오류 / JSON 파싱 실패 / 빈 응답 |
| 3 | 재시도하지 않고 즉시 `rule_based_commentary()` 호출 |
| 4 | 자산배분·지표에서 규칙 기반 문장 2~4개 생성 |
| 5 | `Commentary(source="fallback")` 반환 |
| 6 | 배너에 `AI 진단 코멘트 · 규칙 기반` 제목으로 표시 |

### 폴백 문장 생성 규칙

| 조건 | 생성 문장 |
|---|---|
| 최대 비중 자산군 > 40% | "{자산군} 비중이 {n}%로 포트폴리오의 상당 부분을 차지합니다." |
| 변동성 계산 가능 | "연환산 변동성은 {n}%로 {높은/보통/낮은} 수준입니다." |
| 샤프지수 계산 가능 | "샤프지수는 {n}로, 감수한 위험 대비 {양호한/아쉬운} 성과를 보였습니다." |
| 최대 상관계수 > 0.5 | "{A}와 {B}의 상관계수가 {n}로 높아 분산 효과가 제한적입니다." |
| 위 전부 해당 없음 | "리스크 지표를 계산하기에 데이터가 충분하지 않습니다." |

### 수용 기준

- [ ] `ANTHROPIC_API_KEY`를 지우고 실행해도 코멘트 영역이 채워진다
- [ ] 폴백 코멘트도 실제 수치를 인용한다
- [ ] 사용자가 LLM 코멘트와 폴백을 구분할 수 있다 (FR-706)
- [ ] 재시도로 인한 지연이 없다

## UC-05. 일부 종목 가격 조회 실패

| 항목 | 내용 |
|---|---|
| **목표** | 종목 하나의 데이터 문제가 대시보드 전체를 무너뜨리지 않는다 |
| **선행조건** | 일부 종목의 `/candles` 조회 실패 (`unsupported-symbol`, 신규 상장, 빈 캔들 등) |
| **대응 요구사항** | FR-204, NFR-204 |

### 흐름

| # | 시스템 |
|---|---|
| 1 | 종목별 `GET /api/v1/candles` 루프 실행 (스로틀 적용) |
| 2 | `unsupported-symbol`·`stock-not-found`·빈 캔들 → `failed` 리스트에 수집 (예외 전파 안 함) |
| 3 | 성공 종목만으로 `prices` DataFrame 구성 |
| 4 | 제외된 종목의 비중을 뺀 뒤 **나머지 비중을 재정규화** |
| 5 | 재정규화된 비중으로 포트폴리오 수익률 계산 |
| 6 | `RiskMetrics.excluded_tickers`에 실패 종목 기록 |
| 7 | 화면에 `⚠ 2개 종목의 가격 데이터를 가져오지 못해 지표 계산에서 제외했습니다` 표시 |

### 중요 설계 결정

**자산배분 차트에는 제외 종목이 그대로 포함된다.** 자산배분은 현재 평가금액만 필요하므로 가격 히스토리 없이도 정확하다. 리스크 지표만 축소된 모집단으로 계산된다.

이 차이를 사용자가 오해하지 않도록, 경고 문구에 "지표 계산에서"라는 범위를 명시한다.

### 수용 기준

- [ ] 실패 종목이 있어도 나머지로 지표가 계산된다
- [ ] 재정규화 후 비중 합계가 1.0이다
- [ ] 제외 사실이 화면에 표시된다
- [ ] 자산배분 차트는 전체 종목을 반영한다

## UC-06. 종목 메타 조회 실패 / 미분류 종목

| 항목 | 내용 |
|---|---|
| **목표** | 메타데이터가 없거나 미지의 enum이 와도 정상 동작한다 |
| **대응 요구사항** | FR-301c, FR-303, FR-106b |

### 흐름 A — `GET /api/v1/stocks` 전체 실패

| # | 시스템 |
|---|---|
| 1 | 종목 메타 조회가 예외로 종료 |
| 2 | `meta = {}` 로 진행 (예외 전파 안 함) |
| 3 | `classify(..., meta=None)` → `marketCountry` 축약 분류 |
| 4 | KR → 국내주식, US → 해외주식 |
| 5 | 도넛 차트가 2개 슬라이스로 정상 렌더링 |
| 6 | `⚠ 종목 정보를 가져오지 못해 자산군을 단순 분류했습니다` 표시 |

### 흐름 B — 미지의 enum 값

| # | 시스템 |
|---|---|
| 1 | `securityType`이 스펙에 없는 새 값 (예: `CRYPTO_ETP`) |
| 2 | 모델이 `str`로 담아 통과 (StrEnum 강제 파싱 안 함) |
| 3 | 분류 알고리즘 1~6단계 전부 미매치 |
| 4 | 7단계 → `AssetClass.OTHER` ("기타") |

### 흐름 C — 매핑 파일 문제

| 분기 | 조건 | 처리 |
|---|---|---|
| C1 | `asset_class_map.yaml` 없음 | 기본 분류기 사용, 경고 로그 |
| C2 | YAML 문법 오류 | 동일 |

### 수용 기준

- [ ] 분류 실패가 예외를 발생시키지 않는다
- [ ] `stocks` 호출이 죽어도 자산배분 차트가 뜬다
- [ ] 미지의 enum이 `ValidationError`를 유발하지 않는다
- [ ] 매핑 파일이 없어도 앱이 실행된다

> **개선 경로**: 자동 분류가 틀렸으면 `config/asset_class_map.yaml`의 `overrides`에 종목코드를 추가한다. ETF 하위 분류가 안 잡히면 `etf_keywords`에 키워드를 추가한다. README에 안내한다.

| 7 | AI 코멘트가 집중 리스크를 지적 |

### 수용 기준

- [ ] 히트맵 자리에 안내 문구가 표시된다
- [ ] 다른 5개 블록은 정상 렌더링된다
- [ ] HHI가 `1.00`으로 표시된다

> 현금 자산군은 상관계수 계산에서 제외되므로(DATA_DESIGN §4.8), "국내주식 + 현금"만 보유해도 이 경로를 탄다.

## UC-09. API 호출 한도 초과

| 항목 | 내용 |
|---|---|
| **목표** | 429 응답을 재시도로 악화시키지 않는다 |
| **대응 요구사항** | NFR-202, PRD R6 |

### 흐름

| # | 시스템 |
|---|---|
| 1 | 캔들 루프 중 HTTP 429 `rate-limit-exceeded` |
| 2 | `Retry-After` 헤더 값만큼 대기 후 재시도 (최대 3회) |
| 3 | 스로틀이 `X-RateLimit-Remaining`을 갱신해 이후 호출 간격을 늘림 |
| 4 | 3회 모두 실패하면 해당 종목만 `failed`에 넣고 루프 계속 |
| 5 | 계좌 API에서 429가 나면 `RateLimitError` → 캐시 복원 |
| 6 | 캐시 없으면 → UC-02 (샘플 데이터) |

### 수용 기준

- [ ] `Retry-After`를 존중해 대기한다 (임의 백오프 아님)
- [ ] 한 종목의 429가 전체 루프를 중단시키지 않는다
- [ ] 사용자에게 원인이 명확히 전달된다

> **예방이 우선이다.** 헤더 기반 적응형 스로틀(API_DESIGN §11.2)과 1시간 캔들 디스크 캐시가 정상 작동하면 이 경로는 거의 발생하지 않는다.

## UC-12. 토큰 만료 중 요청

| 항목 | 내용 |
|---|---|
| **목표** | 토큰 만료를 무한 재발급 루프 없이 처리한다 |
| **대응 요구사항** | FR-101a, FR-101b |

### 흐름

| # | 시스템 |
|---|---|
| 1 | 캐시된 토큰으로 `/holdings` 호출 |
| 2 | 401 `expired-token` 수신 |
| 3 | `refreshed == False` 확인 → `POST /oauth2/token` 재발급 (1회) |
| 4 | 새 토큰을 `token.json`에 저장 (권한 0600) |
| 5 | `refreshed = True` 설정 후 동일 요청 재시도 |
| 6 | 성공 |

### 예외 흐름

| 분기 | 조건 | 처리 |
|---|---|---|
| 3a | 재발급도 실패 | `AuthenticationError` → 목업 폴백 (UC-02) |
| 5a | 재발급 후에도 401 | `refreshed == True`이므로 **재발급하지 않고** `AuthenticationError` |

### 수용 기준

- [ ] 401 → 재발급은 요청당 최대 1회
- [ ] 재발급 루프가 발생하지 않는다
- [ ] `token.json` 권한이 `0600`이다
- [ ] 정상 상황에서는 앱을 여러 번 실행해도 재발급이 없다

> **왜 P0인가**: 토큰 재발급이 **이전 토큰을 즉시 무효화**한다. 루프가 생기면 자기 자신의 토큰을 계속 죽이면서 `AUTH` 레이트리밋만 소모한다. 개발 중 다른 터미널 세션도 같이 죽는다.
